POST-Centric API Pattern - The Smart Approach

Why using POST for everything is actually more reliable than REST purism.

🚫 Problems with RESTful Methods

  • GET: ~2KB URL limit, visible parameters
  • PUT/DELETE: Blocked by firewalls
  • PATCH: Inconsistent proxy support
  • OPTIONS: CORS preflight issues

✅ POST-Everything Benefits

  • No Size Limits: Request body can be huge
  • Firewall Friendly: POST always works
  • Consistent Errors: Same error handling
  • Flexible Payloads: Combine operations

Traditional REST vs POST-Centric

❌ Traditional REST Problems

// GET with too many parameters (URL length exceeded) GET /api/users?department=engineering&skills=javascript,typescript,react&experience=5-10&location=remote&startDate=2020-01-01&endDate=2023-12-31&includeMetadata=true&sort=name,asc&limit=50&offset=0 // PUT blocked by corporate firewall PUT /api/users/123 (BLOCKED) // DELETE blocked by proxy DELETE /api/users/123 (BLOCKED)

✅ POST-Centric Solution

// Everything via POST - always works! POST /api/unified { "action": "GET_USERS", "filters": { "department": "engineering", "skills": ["javascript", "typescript", "react"], "experience": "5-10", "location": "remote", "dateRange": { "start": "2020-01-01", "end": "2023-12-31" } }, "options": { "includeMetadata": true, "pagination": { "limit": 50, "offset": 0 }, "sorting": [{ "field": "name", "direction": "asc" }] } }
